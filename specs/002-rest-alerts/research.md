# Research: Rest-End Alerts (002)

Package versions checked on pub.dev on 2026-11-13.

## R1. Why there is no sound today

- **Finding**: `SystemSound.play(SystemSoundType.alert)` is a no-op on Android (only `click` is
  implemented there), so the alarm callback runs but nothing is heard.
- **Decision**: replace it with a bundled chime played through a real audio player.

## R2. Foreground chime

- **Decision**: `audioplayers` ^6.8 playing a bundled asset `assets/sounds/rest_chime.ogg` with an
  `AudioContext` of Android usage `notificationEvent`, content type `sonification`, audio focus
  `gainTransientMayDuck`; iOS category `ambient` (respects the mute switch, mixes with music).
- **Rationale**: the notification usage follows the ringer/notification volume and is muted in
  silent / DND mode (FR-002); transient-may-duck lowers but does not stop music (SC-006).
- **Asset**: an original two-tone chime (~0.7 s, 880 Hz → 1320 Hz with soft attack/decay)
  generated by a script, OGG Vorbis, < 30 KB. No third-party audio. The same file is copied to
  `android/app/src/main/res/raw/rest_chime.ogg` for the notification channel sound.
- **Alternatives**: `just_audio` (heavier, more than needed); `flutter_ringtone_player` (plays the
  system alarm/notification tone — not pleasant/consistent, and alarm stream ignores silent mode).

## R3. Background notification

- **Decision**: `flutter_local_notifications` ^23 `zonedSchedule` with `timezone` ^0.11
  (`tz.initializeTimeZones()`; schedule in `tz.UTC`, so no device-timezone lookup is needed).
  Payload `workout` → on tap, navigate to `/workout` (also via `getNotificationAppLaunchDetails` on
  cold start).
- **Schedule mode**: `AndroidScheduleMode.exactAllowWhileIdle` when
  `canScheduleExactNotifications()` is true, otherwise `inexactAllowWhileIdle` (FR-013). Manifest
  declares `SCHEDULE_EXACT_ALARM` (user-grantable; Android 14+ denies by default). Do **not** use
  `USE_EXACT_ALARM` (Play policy reserves it for alarm/calendar apps).
- **Channels**: Android channel sound/vibration cannot change after creation, so four channels:
  `rest_sound_vibrate`, `rest_sound`, `rest_vibrate`, `rest_silent` (all importance high, custom
  sound `rest_chime`). The channel is chosen from the alert settings when scheduling; toggling a
  setting while a timer runs reschedules (FR-007).
- **Single pending alert**: fixed notification id `4201` — scheduling replaces, `cancel(4201)`
  removes pending and shown (FR-005, FR-006, FR-010).
- **No duplicate in foreground (FR-009)**: the notification is scheduled only while the app is not
  in the foreground. An `AppLifecycleListener` calls `onBackground()` (hide/pause → schedule if a
  timer is running and not yet past 0) and `onForeground()` (resume → cancel pending + clear shown).
  The in-app `Timer` handles the foreground chime/vibration.
- **Process death**: the alarm is held by the OS, so it fires even if the app process is killed
  (FR-004).
- **Reboot (FR-014)**: do **not** register the plugin's `ScheduledNotificationBootReceiver`, so
  pending rest alarms are dropped on reboot instead of firing late.
- **Alternatives**: a foreground service with a ticking notification (heavier, needs a
  FOREGROUND_SERVICE type and a persistent notification — overkill for a 60 s timer); `android_alarm_manager_plus`
  (runs Dart in the background; unnecessary since the notification itself is the alert).

## R4. Permissions and Settings links

- **Decision**: request `POST_NOTIFICATIONS` via the plugin's
  `requestNotificationsPermission()` the first time a rest timer starts, recording
  `notif_permission_asked=true` in the settings table so it is asked at most once automatically
  (FR-011). Settings shows status from `areNotificationsEnabled()` and
  `canScheduleExactNotifications()`; buttons use `app_settings` ^9
  (`AppSettings.openAppSettings(type: AppSettingsType.notification)`) and the plugin's
  `requestExactAlarmsPermission()` (opens the exact-alarm settings page).
- **Alternatives**: `permission_handler` (larger surface than needed; the notification plugin
  already covers both permissions).

## R5. Testability

- **Decision**: all platform calls go behind a `RestAlerts` interface (contract in
  `contracts/rest-alerts.md`) provided by Riverpod; tests override it with a recording fake.
  `RestTimerController` owns the rules (when to schedule/cancel/chime) and is unit-tested with the
  fake and the injectable clock.
